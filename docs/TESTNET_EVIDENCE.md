## How this ran

- Real Rails pages in `RAILS_ENV=development` on a dedicated database, with digested assets and the strict CSP, checked in journey A. **Production mode was not run.**
- Headless Google Chrome over DevTools, a separate browser context per user, real pointer clicks. Wallets are `test/javascript/support/test_provider.js` with `allowSend`; the harness adds a check before every send that the chain is 11155111 and the target is the factory, EURC or a canonical Safe.
- **Solid Queue is real:** `bin/jobs`, with the recurring `ChainSyncSchedulerJob` every minute. Development normally uses the async adapter, so `test/e2e/serve.sh` sets `SOLID_QUEUE_IN_DEV=1`, a one-line switch in `config/environments/development.rb`, and loads `db/queue_schema.rb` into the same database. `SOLID_QUEUE_IN_PUMA` was not used. Mail is the real job writing real messages through letter_opener; the harness follows the link in the delivered mail. **No external mail delivery was tested.**
- **Outage is real:** the server reaches its RPC through a harness proxy that can refuse every connection, and the browser's RPC requests are blocked over DevTools. No application code is stubbed.
- **One setup step skips the UI:** the viewer role was set directly in the database, because no screen can set it. Everything else went through the UI or the JSON API the pages use.
- Independent verification is `test/e2e/chain.mjs`: raw JSON-RPC, selectors written out, its own encoder, no app code.
- The harness lives in `test/e2e/`. It is not picked up by `bin/rails test` (only `*_test.rb`), by `node --test` in `test/javascript`, or by CI.

To run it again:

```sh
FT_E2E_OUT=<dir outside the repo> test/e2e/serve.sh reset
FT_E2E_KEYS=<keys.json outside the repo> FT_E2E_OUT=<same dir> FT_E2E_SCREENS=<dir> \
  node --experimental-websocket test/e2e/run.mjs A B B_eurc C C_token D E E_token F G Z
```

The order matters: F needs EURC in the Safe. `B_eurc` needs at least 9 EURC on the funded address. A later run spends again and gets new Safes.

## Found and not changed

These are product decisions, so they are reported here and left as they are.

- **ETH in a Safe appears in no balance.** The dashboard said `0,00 EURC` while the Safe held 0.0018 ETH. The ETH was visible only as activity rows.
- **A native payout shows no amount or recipient in activity.** The row says only `Voorstel uitgevoerd`, because a native transfer emits no event of its own. EURC payouts do show both.
- **A proposal for more than the balance is still labelled ready.** Signatures are valid, so the UI says ready, and the refusal comes when someone clicks execute.
- **A reverted over-balance proposal blocks its nonce** until the balance suffices or a rejection is executed, as the contract requires. The rejection stays available on the page, but the refusal message does not point to it.
- **No screen can set the viewer role**, although the role is enforced.
- **A fully consistent server-side tamper cannot be detected by the client.** With recipient, target and hash all changed, the review page shows the attacker's address and hash in full; the server refuses the resulting signature because it recomputes the hash. A compromised server that also accepted it is only caught by comparing the hash through another channel, as the threat model already says.
- **Public RPC endpoints can lag.** Straight after a receipt, `latest` returned the previous block twice in this run (harness reads). The app showed no wrong result from this, but it was not tested on purpose, and a lagging server read after execution could still bring back the stale page of bug 2.

## Not verified

- Real wallet extensions, phones and hardware wallets. All signing used the test provider.
- The Safe{Wallet} UI. Only the link format, its HTTP 200, and Safe's Transaction Service reading the Safe as owners 3, threshold 2, version 1.4.1+L2 were checked.
- Any real-money ramp, any mainnet, and production mode (`force_ssl`, separate queue database, real mail).
- `ExecutionFailure` on a live Safe. Unreachable through this product, as explained under journey E.
- A chain reorg. None occurred during the run.
- A Mac sleep during the run left one `ChainSyncJob` marked failed (`ProcessPrunedError`). The next recurring run caught up, and nothing was lost. Treated as an effect of this environment, not a product bug.
